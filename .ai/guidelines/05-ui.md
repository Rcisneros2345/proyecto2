# 05 · Interfaz

Fuente de verdad visual: `docs/ui/UI_DESIGN_PRINCIPLES.md` y las propuestas aprobadas en
`.ui-work/01-propuestas/`. Esta guía solo añade las reglas de convivencia con el resto.

## Criterio

Cada elemento visual debe reducir el tiempo que tarda el usuario en **encontrar** y
**entender** lo que busca. Si no hace eso, sobra. Nada decorativo.

## Reutiliza antes de inventar

`<x-data-table>` · `<x-badge>` · `<x-filter-bar>` · `<x-stat-card>` · `<x-drawer>` ·
`<x-page-header>` · `<x-navigation-menu>` · `<x-academia.ciclo-selector>` ·
`partials/empty-state` · `partials/donut` · `partials/sparkline`.

Crear un componente nuevo que duplique a uno existente es deuda inmediata.

## Límites del trabajo visual

- No se tocan controllers, modelos, consultas ni rutas. Si la vista necesita un dato que no
  recibe: `[GAP: BACKEND]` con el detalle, y lo pide `team-lead`.
- No se consulta la base desde Blade.
- No se renombra una vista, partial o componente sin `route-safety` e `impacto`.
- Los partials se comparten entre pantallas: cambiar la variable que espera un partial
  rompe a sus otros consumidores **en silencio**. Corre `php scripts/impacto.php`.

## Patrones del sistema

- **Estado**: badge con color **y** texto **y** tiempo relativo. El color solo no basta.
- **Listados**: filtros arriba, columnas esenciales, detalle en drawer o fila expandible,
  paginación y conteo visibles.
- **Sincronizaciones**: resultado por ítem, nunca un éxito/error global.
- **Acciones peligrosas**: confirmación que obliga a leer qué se va a borrar.
- **Estados vacíos**: qué pasó y qué hacer. **Errores**: concretos y accionables.
- Accesibilidad: contraste en claro y oscuro, foco visible, `<th>` reales, `<label>`
  asociado, `aria-label` en botones de ícono, tablas que se vuelven tarjetas en móvil.

Si el frontend no refleja un cambio: `npm run build` / `npm run dev` (regla de Boost).
